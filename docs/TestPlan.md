## 2. Объект тестирования (Test Items)

### 2.1 Описание проекта
**StudentCounter** - мобильное приложение для управления учебными задачами студентов с функциями:
- Управление предметами
- Создание и редактирование задач
- Установка дедлайнов
- Настройка множественных уведомлений
- Локальное хранение данных

### 2.2 Компоненты тестирования

#### 2.2.1 Функциональные модули
- Модуль управления предметами (SubjectsContext, SubjectCard)
- Модуль управления задачами (TasksContext, TaskCard)
- Модуль уведомлений (NotificationService)
- Модуль хранения данных (StorageService)
- UI компоненты (NotificationPicker, формы создания/редактирования)

#### 2.2.2 Экраны приложения
- Главный экран со списком задач (TasksPage)
- Экран списка предметов (SubjectsPage)
- Модальное окно создания задачи (AddTaskPage)
- Модальное окно редактирования задачи (EditTaskPage)
- Модальное окно создания предмета (AddSubjectPage)

### 2.3 Атрибуты качества (ISO 25010)

#### 2.3.1 Функциональная пригодность
- **Функциональная полнота:** Реализованы все требования из SRS
- **Функциональная корректность:** Функции работают без ошибок
- **Функциональная целесообразность:** Функции соответствуют потребностям пользователей

#### 2.3.2 Производительность
- **Временная характеристика:** Отклик UI < 300 мс
- **Использование ресурсов:** Потребление памяти < 100 MB
- **Емкость:** Поддержка до 1000 задач без деградации

#### 2.3.3 Совместимость
- **iOS:** 13.0 - 17.x
- **Android:** 5.0 (API 21) - 14.0 (API 34)
- **Разрешения экрана:** 320px - 1920px ширина

#### 2.3.4 Удобство использования
- **Интуитивность:** Новый пользователь выполняет основные задачи без обучения
- **Доступность:** Поддержка VoiceOver (iOS) и TalkBack (Android)
- **Эстетика UI:** Соответствие Material Design и iOS HIG

#### 2.3.5 Надежность
- **Устойчивость к сбоям:** Приложение не падает при некорректных данных
- **Восстанавливаемость:** Данные восстанавливаются после сбоя
- **Доступность:** Работа в офлайн-режиме 100% времени

## 4. Аспекты тестирования (Features to be Tested)

### 4.1 Функциональные требования

#### FR-1: Управление предметами
- **FR-1.1:** Создание предмета с уникальным названием и цветом
- **FR-1.2:** Просмотр списка предметов с количеством задач
- **FR-1.3:** Удаление предмета и связанных задач

#### FR-2: Управление задачами
- **FR-2.1:** Создание задачи с названием, предметом, дедлайном, описанием
- **FR-2.2:** Просмотр списка задач с сортировкой по дедлайну
- **FR-2.3:** Редактирование всех полей задачи
- **FR-2.4:** Удаление задачи
- **FR-2.5:** Отметка задачи выполненной/невыполненной

#### FR-3: Система уведомлений
- **FR-3.1:** Настройка множественных уведомлений для задачи
- **FR-3.2:** Отправка уведомлений в установленное время
- **FR-3.3:** Запрос разрешения на уведомления
- **FR-3.4:** Уведомление со звуком и вибрацией

#### FR-4: Хранение данных
- **FR-4.1:** Сохранение предметов в AsyncStorage
- **FR-4.2:** Сохранение задач в AsyncStorage
- **FR-4.3:** Автоматическое сохранение после изменений
- **FR-4.4:** Загрузка данных при запуске приложения

### 4.2 Нефункциональные требования

#### NFR-1: Производительность
- **NFR-1.1:** Время запуска < 2 секунд
- **NFR-1.2:** Отклик UI на действия < 300 мс
- **NFR-1.3:** Плавная анимация 60 FPS
- **NFR-1.4:** Поддержка 1000 задач без замедления

#### NFR-2: Надежность
- **NFR-2.1:** Работа без интернета
- **NFR-2.2:** Точность уведомлений ±1 минута
- **NFR-2.3:** Восстановление данных после сбоя
- **NFR-2.4:** Отсутствие критических ошибок

#### NFR-3: Удобство использования
- **NFR-3.1:** Создание задачи за ≤ 5 шагов
- **NFR-3.2:** Поддержка альбомной и портретной ориентации
- **NFR-3.3:** Поддержка темной/светлой темы системы
- **NFR-3.4:** Размер кнопок ≥ 44pt (iOS) / 48dp (Android)

#### NFR-4: Совместимость
- **NFR-4.1:** iOS 13.0+
- **NFR-4.2:** Android 5.0+ (API 21+)
- **NFR-4.3:** Экраны от 4" до планшетов
- **NFR-4.4:** Различные плотности экрана

## 5. Подходы к тестированию (Test Approach)

### 5.1 Типы тестирования

#### 5.1.1 Функциональное тестирование
**Цель:** Проверка соответствия функциональным требованиям

**Методы:**
- Ручное тестирование UI
- Тестирование use case сценариев
- Граничное тестирование (boundary testing)
- Тестирование эквивалентных классов

**Инструменты:**
- Ручное выполнение на реальных устройствах
- iOS Simulator / Android Emulator
- Expo Go для быстрого тестирования

#### 5.1.2 UI/UX тестирование
**Цель:** Проверка удобства использования и дизайна

**Методы:**
- Проверка соответствия mockups
- Тестирование различных размеров экранов
- Проверка доступности (accessibility)
- Тестирование жестов и анимаций

**Инструменты:**
- Ручное тестирование
- React Native Debugger
- Expo DevTools

#### 5.1.3 Интеграционное тестирование
**Цель:** Проверка взаимодействия компонентов

**Методы:**
- Тестирование интеграции Context ↔ Services
- Тестирование AsyncStorage API
- Тестирование Expo Notifications API
- Тестирование навигации (Expo Router)

**Инструменты:**
- Jest для unit/integration тестов
- React Native Testing Library

#### 5.1.4 Системное тестирование
**Цель:** Проверка работы приложения как единой системы

**Методы:**
- End-to-End тестирование сценариев
- Тестирование на реальных устройствах
- Проверка разрешений системы
- Тестирование уведомлений в фоновом режиме

**Инструменты:**
- Ручное тестирование
- Detox (опционально для E2E)

#### 5.1.5 Нефункциональное тестирование

**Performance Testing:**
- Тестирование времени запуска
- Тестирование отклика UI
- Нагрузочное тестирование (1000+ задач)
- Профилирование памяти

**Compatibility Testing:**
- Тестирование на iOS 13, 14, 15, 16, 17
- Тестирование на Android 5, 7, 10, 12, 13, 14
- Тестирование на разных разрешениях экрана
- Тестирование на планшетах

**Reliability Testing:**
- Тестирование восстановления после сбоя
- Тестирование работы в режиме низкой памяти
- Тестирование корректности сохранения данных

#### 5.1.6 Регрессионное тестирование
**Цель:** Проверка отсутствия новых ошибок после изменений

**Методы:**
- Повторное выполнение основных тест-кейсов
- Smoke testing после каждого билда
- Проверка критических путей

### 5.2 Уровни тестирования

| Уровень | Описание | Ответственность |
|---------|----------|-----------------|
| Unit Testing | Тестирование отдельных функций и компонентов | Разработчики |
| Integration Testing | Тестирование взаимодействия модулей | Разработчики |
| System Testing | Тестирование приложения целиком | Тестировщики |
| Acceptance Testing | Проверка соответствия требованиям заказчика | Заказчик + Тестировщики |

## 6. Представление результатов (Pass / Fail Criteria)

### 6.1 Критерии приемки

#### 6.1.1 Функциональные критерии
- ✅ Все функциональные требования из SRS реализованы
- ✅ Успешное выполнение 100% позитивных тест-кейсов
- ✅ Корректная обработка 95%+ негативных сценариев
- ✅ Все use case сценарии выполняются без ошибок

#### 6.1.2 Нефункциональные критерии
- ✅ Время запуска приложения < 2 секунд (на устройствах среднего класса)
- ✅ Отклик UI < 300 мс для всех действий
- ✅ Поддержка минимум 500 задач без деградации производительности
- ✅ Приложение стабильно работает на всех целевых платформах
- ✅ Уведомления приходят с точностью ±2 минуты

#### 6.1.3 Качество кода
- ✅ Отсутствие критических ошибок (severity: critical)
- ✅ Не более 5 некритических багов (severity: medium)
- ✅ TypeScript компилируется без ошибок
- ✅ ESLint проверка без критических предупреждений

### 6.2 Метрики тестирования

| Метрика | Целевое значение | Формула |
|---------|------------------|---------|
| Test Coverage (Покрытие) | ≥ 80% | (Протестированные требования / Всего требований) × 100% |
| Pass Rate (Успешность) | ≥ 95% | (Passed тесты / Всего тестов) × 100% |
| Defect Density (Плотность дефектов) | ≤ 2 дефекта/модуль | Всего дефектов / Количество модулей |
| Defect Resolution Rate | ≥ 90% в течение спринта | Исправленные дефекты / Всего дефектов |

### 6.3 Критерии завершения тестирования

**Критерии выхода (Exit Criteria):**
1. Все запланированные тест-кейсы выполнены
2. Pass rate ≥ 95%
3. Все критические и высокие дефекты исправлены
4. Регрессионное тестирование пройдено успешно
5. Производительность соответствует требованиям
6. Получено одобрение заказчика (Acceptance Testing)

**Критерии приостановки (Suspension Criteria):**
1. Критические дефекты блокируют тестирование
2. Сборка приложения не запускается
3. Более 50% тестов падают (build is unstable)
4. Изменения в требованиях требуют пересмотра тест-плана
